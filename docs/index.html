MCP 101

A common protocol for giving AI applications tools, context, and workflows.

Why MCP exists

AI apps need a repeatable way to discover and call external capabilities without every integration becoming a one-off plugin.

  • Clients connect to servers and expose capabilities to the model.
  • Servers publish tools, resources, prompts, and optional apps.
  • Hosts are the applications people use: editors, chat apps, agents, and CLIs.

The basic request flow

  1. The host starts or connects to an MCP server.
  2. The client asks the server what it supports.
  3. The model chooses a tool, resource, or prompt when it needs one.
  4. The user approves calls when the host requires confirmation.
  5. The server returns structured results for the model to use.

Core building blocks

Tools

Actions the model can call, such as searching docs, buying a product, or filing an issue.

Resources

Readable context, such as files, inventory, database records, or generated documents.

Prompts

Reusable prompt templates that help clients start useful model interactions.

Agents + MCP

Now the agent code becomes the MCP client.

What is an agent framework?

An agent framework coordinates model calls, tool schemas, tool execution, memory or state, and final responses.

The model decides

  • When it needs a tool
  • Which arguments to send
  • How to use the result

The framework manages

  • Tool registration
  • Async execution
  • Retries and final output

Build an MCP server

FastMCP gives us a compact Python API for tools, resources, prompts, and transports.

FastMCP server skeleton


from fastmcp import FastMCP

mcp = FastMCP("Pamela's Bakery")

INVENTORY = {
    "Croissant": {"price": 3.50, "quantity": 40},
    "Sourdough Loaf": {"price": 7.00, "quantity": 20},
    "Cinnamon Roll": {"price": 4.25, "quantity": 30},
}

if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="0.0.0.0", port=8420)

Turn Python functions into MCP tools


from typing import Annotated

@mcp.tool
async def buy_product(
    product_name: Annotated[str, "Name of the product to buy"],
    quantity: Annotated[int, "Number of items to buy"],
) -> str:
    """Buy a product from the store, reducing its inventory."""
    if product_name not in INVENTORY:
        return f"Error: '{product_name}' not found."

    product = INVENTORY[product_name]
    if product["quantity"] < quantity:
        return "Error: Not enough stock."

    product["quantity"] -= quantity
    return f"Bought {quantity}x {product_name}."

Advanced server features

MCP servers can do more than return plain strings.

Beyond basic tools

  • Apps: Render UI in capable hosts.
  • Elicitation: Ask the user for structured input mid-tool call.
  • Progress: Report long-running work.
  • Background tasks: Keep work moving after the initial request.
  • Resources: Publish read-only context.
  • Prompts: Package repeated workflows.

Use Prefab UI to return interactive components, then use elicitation to confirm a purchase before changing state.

  • @mcp.tool(app=True) for an inventory chart.
  • Product catalog cards with prices and stock badges.
  • ctx.elicit(...) for purchase confirmation.

Purchase confirmation


response = await ctx.elicit(
    message=f"Buy {quantity}x {product_name} for ${total:.2f}?",
    response_type=PurchaseConfirmation,
)

if response.action != "accept" or not response.data.confirm:
    return "Purchase cancelled."

The server can pause and ask the human before committing the action.

Authenticated MCP servers

When tools access user-specific data, the server needs to know who is calling.

MCP auth in one slide

  • MCP auth builds on OAuth 2.1.
  • The server advertises protected resource metadata.
  • The client discovers how to authorize.
  • Dynamic client registration or client metadata can be part of the flow.
  • The host gets a token, then retries the MCP request.
Use this as the conceptual bridge before showing Keycloak. Avoid diving too deep into every acronym until the diagram or demo.

Keycloak gives us a local-friendly IAM

Identity server

  • Users and test credentials
  • OAuth clients
  • Scopes and audience

MCP server

  • Validates access tokens
  • Requires openid and mcp:access
  • Can identify the caller

FastMCP Keycloak provider


from fastmcp.server.auth.providers.keycloak import KeycloakAuthProvider

auth = KeycloakAuthProvider(
    realm_url="https://example.com/realms/pycon",
    base_url="http://localhost:8420",
    required_scopes=["openid", "mcp:access"],
    audience="product-store",
)

mcp = FastMCP("Pamela's Bakery", auth=auth)

Next steps

Take the working server from tutorial code to something you can operate.

Deployment checklist

  • Pick a transport and hosting model intentionally.
  • Keep secrets out of source control and demo configs.
  • Log tool calls without logging sensitive payloads.
  • Rate-limit expensive or state-changing tools.
  • Design tool descriptions as part of your API surface.
  • Test with both direct MCP tools and LLM-driven clients.

Security questions to ask every server

  • Who is allowed to call this tool?
  • What data can the tool read or mutate?
  • Does the user understand when state will change?
  • Can prompt injection alter the server's authority?
  • What happens when the model passes surprising arguments?
